01 Routing

The ten-second router

The whole intake decision in one table. Find the row that matches what you have in hand; reach for what sits beside it. First match wins.

You have Reach for
A trivial edit, or a pure question do it inline — no ceremony
Staged execution of a plan — one exists, or you’ll write one /orchestrate
A meaningful repo change from a raw request /build-system Sizes its docs to the work: PRD + Plan for large or ambiguous, one Spec for medium, neither for small.
GitHub issues to resolve, or an existing PR to ship /ship-issues PR-stage review + fix + promote → /pr-auto-review; a PR behind main → /auto-merge-main.
A non-code or mixed deliverable — research, proposal, docs /teamwork
A long unattended goal that must not stop for questions /auto-run
A batch of decisions for the human /make-it-easy  visual, or  /askme  inline
A plan to stress-test with the human /grill-me

First match wins, top to bottom.

03 Review

Review tiers

Three ascending tiers, cheapest to widest, one shared finding format. Wrap any of them in a fix loop when one pass isn’t enough.

Claude reviewer Codex reviewer Findings deduped & validated against the actual diff.
Tier What runs Round cap
/quick-review one Claude pass; a fresh-eyes sub-agent when reviewing its own edits 5 rounds
/dual-review + one detached Codex on the same scope, deduped 5 rounds
/lens-review one Claude + one Codex per lens, read-only — the widest net 3 rounds

Caps apply when a tier is wrapped in /review-fix-loop; the loop stops earlier on convergence, steady-state, or regression. Severity: critical · high · medium · low · nit.

Convergence is the goal.
The cap is the cost guard.

Two reviewers from different model families make less-correlated mistakes than two passes of the same model. Dedup what they agree on; investigate what they don’t.

04 Composition

The composition map

The commands aren’t isolated — they nest. The vehicles you pick from the router, the drivers that wrap them, the human-decision lane that feeds them, and the one review engine they all run through.

Claude Codex Dashed enclosure = wraps what’s inside.

If you take one reading of this map: the reviewer leaves at the bottom are shared. /build-system and /ship-issues run their work through the same tiers and the same convergence discipline — the fix-loop. /orchestrate reaches for the same reviewer leaves in a single post-execution once-over instead of the loop. What differs across the three is mostly what each wraps around the review, not the reviewers it reaches for.

05 Delegation

Delegation & model tiering

Every dispatched sub-agent gets a model tier, and the tier is picked by the shape of the work, not its importance — important-but-mechanical work stays cheap, because verification catches loud errors cheaply.

Strongest → cheapest

Fable Not agent-selectable. The human names it or dispatches it; no escalation test reaches it, and no agent talks itself into it.
Opus The top tier an agent may pick, and the default for thinking and execution: reviews, fixes, synthesis, planning, conductors, and meaningful multi-step builds.
Sonnet Extraordinarily simple, single-unit work — plus two structural rules: unbounded fan-outs, and the mechanical Codex drivers, both pinned here.
Haiku Never for project or coding work; its one use is volume reading — stages that ingest hundreds of items and return compressed digests.

The escalation test, when two adjacent agent-selectable tiers are both plausible: take the higher one only when both conditions hold.

Rule — omission is not neutral

Pass an explicit model: on every dispatch. An unpinned sub-agent inherits the session model — leave the field off on an expensive session and the child silently runs at the top tier, with no one deciding that. It isn’t absolute: a few workflow stages inherit the session model on purpose (documented per stage), and a subagent-model environment override can set the tier outright. (This rule exists because it happened: a session once launched three top-tier explorers for work a cheaper tier should have carried.)

The full policy — the tier guide, the ceiling, the fan-out rules, and the standing exceptions — lives in CLAUDE-global.md.

07 Devbox

The devbox stack

Claude Code runs on an always-on Linux box, not my laptop. Every device I own is a thin client to the same running sessions — they survive laptop lids, network drops, and travel.

Every layer earns its place. None of the pieces are novel — the integrated stack is the point.

The statusline is your instrument panel — the one always-visible strip. Segments worth having:

~/proj ⎇ main opus · high ctx 42% usage 68% host mybox

dir + branch (worktree-aware) · model + effort · context used · usage/quota · anything machine-specific. The chapter ships a build-your-own prompt, not my script.

The full chapter — sizing the box, the access modes, the tmux activity indicators, and why the statusline ships as a prompt rather than a script — is in docs/devbox.md.

08 Porting

Porting the concepts

If your tool is Cursor, Claude Cowork, or the Codex CLI, I can only answer at the concept level — I haven’t verified those platforms’ primitives and won’t pretend otherwise. But the ideas separate cleanly from the implementation.

Ports anywhere

  • The routing tree — a fixed intake decision instead of per-task improvisation.
  • The review ladder and its convergence discipline.
  • The config-feedback rule — one grounded improvement per session.
  • Docs-gated builds, sized to the work.
  • Decision batching at natural boundaries.

Claude-Code-shaped

  • Hooks — the tmux activity indicators ride on them.
  • The subagent primitives — spawning, nesting, model pinning.
  • The skills format itself.
  • If your tool has equivalents, the mapping is yours to make — I’d rather leave it to you than guess at APIs I haven’t used.

None of what ports depends on Claude Code. That’s the whole reason the improvement loop says to port the rule, not the snapshot — the rule outlives any one tool.
